# FIRBO CEO — durable personal sessions and bounded memory
Date: 2026-10-09. Master tracking: [Issue #52](https://github.com/conpol84/javris-clone/issues/52).
Source line: PR #121 stacked on production-tested PR #120, **no replacement** of previous Claude/Codex/specialist work.

## Owner requirement / exact promise boundary

The CEO must remember what a user and the CEO discussed in **previous sessions** without reinterpreting an old command as a new authorization. Each tenant's users should see only their **own CEO conversations**, including readable titles, latest-message previews, search, resume, and new conversation; admins get company audit routes separately, not another user's personal chats.

This phase reuses FIRBO's existing durable `public.conversations` and `public.messages`. Both were already populated (2026-10-09 read-only inventory: 59 conversations / 209 messages across the instance; owner company had prior CEO chats). The CEO Page and TalkConsole previously reset `convo.current=null` on mount and hid prior history. This was not missing database storage but missing scoped UI and cross-session retrieval.

## Implemented architecture (PR #121)

1. **Private history UI** — `ceo-sessions.ts` queries conversations with `organization_id + user_id + agent_id + status=active`, sorted by most recent update, up to 60. Batched previews use at most 360 selected message rows; restoring validates that exact company/user/CEO session before reading up to 220 messages. No other agent, user or company session appears in the personal UI, including to owner/admin. `CeoSessionHistory.tsx` adds previews, search, accessible selection, "new" and localized labels to both CEO Page and TalkConsole.
2. **Continue correctly** — `useCeoSession` waits for previous-session retrieval before enabling the CEO, chooses the latest owned conversation on mount, retains that conversation ID for subsequent `agent-chat` requests (so the model sees same-thread recent turns). Owners can open an older session or start a distinct conversation without deleting old data. Network failures are disclosed; no silent new conversation or fake forgotten history when loading fails. Switching company/user clears the prior UI, audio and pending scope.
3. **Across sessions** — The backend `agent-chat` looks up at most 18 previous CEO conversations and up to 220 recent user/assistant message rows, explicitly filtered by authenticated `organization_id, user_id, agent_id`, excluding current conversation. The pure `ceo-session-recall.ts` selects topical relevant prior user questions and labels old assistant claims `UNVERIFIED`, with bounded length <=1700 characters. No other user/company, stale credentials or secret access is introduced. This is lightweight topic-matched recall, **not** full vector semantic memory or guaranteed permanent recall of every detail.
4. **Ground truth for desktop work** — `agent-chat` additionally supports an authenticated `journal_computer_job` request for a **terminal** `owner`-origin Connector job belonging to that exact user and company. The server loads the real job/worker/result and builds the journal itself. It does not accept a client-written assistant result and never calls an AI model or repeats a device action. Existing message ID equals job UUID for idempotency; an attempt to move one job into another conversation is rejected. The entry distinguishes transport receipt matching from observed objective completion and retains black/locked-screen failure language. This produces a durable CEO history for completed direct work. Jobs still queued/running, device preflight questions without a terminal job and unreconciled results are preserved under Computers; they must not be represented as finished chat history.
5. **Least privilege for LLM context** — CEO memory rows are filtered by `user_id` (or explicitly company-shared metadata), never automatically importing private notes from another user. Leadership financial/approval context is only included for owner/admin/manager; ordinary members' CEO sees their own tasks. Unverified/deleted/expired learned memories stay quarantined. The database's existing broader `public.memories` RLS policy still needs a separate reviewed production-tightening phase before onboarding untrusted outside tenants; backend filtering is not a substitute for DB RLS.

## Safety and evidence acceptance

- Test exact own-user/company/agent `listCeoSessions` and `readCeoSession` paths; unauthorized session IDs denied even for administrators, no accidental cross-org state on role/user switch.
- Test actual Edge handler previous session recall and 8-language learned/deleted/expired memory quarantine; verify no other user's notes, old AI replies flagged unverified, not used as execution permission.
- Test direct journal with actual stored job id, owner-user receipt matching, `completed:false` and black-screen report, non-owner/role denial, idempotency, pending job and cross-conversation conflict; no provider charge or physical execution from a journaling call.
- Run full frontend Vitest, TypeScript/Vite build, actual Edge entrypoint mocked regression tests, exact source bundle/production readback and release gate. **A green simulated CI is NOT proof of the live authenticated user experience**.
- New client and server release must be coordinated. Old backend without journal action leaves CEO direct terminal records in Computers and emits explicit history-warning; never claim the record was saved.
- Viewer history read is permitted only for the viewer's own already existing conversations; creation is limited by existing `WRITER_ROLES`. CEO memory is not a shared public transcript.

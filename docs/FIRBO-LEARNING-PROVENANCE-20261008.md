# FIRBO unverified learning provenance — 8 October 2026

## Changed

This candidate continues exact shared `c7dc3c95276046503a01d98ba6736b9a4056aa98`
without changing tenant permissions, model routes, provider accounting or memory
storage. PR100 already stopped automatic model-to-memory fact insertion; this
stage preserves that behavior and makes its saved proposals attributable.

The actual runner builds `learning` only from its normalized model proposals and
authenticated task/agent/user/claim context. `status: unverified` and the existing
`proposals` list remain. A versioned provenance object records organization,
agent, task, run claim, requesting user, exact saved-report SHA256, normalized
proposal-list SHA256 and a binding SHA256. Model-supplied verification/provenance
fields are ignored. Attribution is not a provider receipt or factual proof.

Hash input is snapshotted before asynchronous work. The report is bounded to
400,000 UTF8 bytes; invalid scope, empty/oversized input or hashing failure omits
the proposals rather than attributing unbound text. The report itself retains
the existing publication path. No proposal can create a memory row here.

The company pulse now describes a partial task-record snapshot. A completed
task status is distinguished from factual correctness or external execution;
saved summaries are labeled unverified data. It no longer declares its snapshot
complete or forbids asking for missing evidence. This instruction is not a
semantic correctness or prompt-injection immunity guarantee.

## Binding format

Schema: `firbo-learning-proposals/v1`. SHA256 uses UTF8 bytes. Proposal-list hash
uses `JSON.stringify` on the already-normalized ordered string array. The binding
hash uses `JSON.stringify` on this fixed ordered array:

`[schema, organization_id, agent_id, task_id, run_claim, requested_by,
source_report_sha256, proposals_sha256]`.

This is deterministic source lineage, not a signature or tamper-proof history.
Anyone able to replace a saved result can recompute its hashes. Any future owner
review/promotion implementation must authenticate current membership, re-read
the authoritative task/claim/result, verify the binding and inspect actual
evidence. It must not treat these hashes as proof of a true fact, current claim,
provider settlement or permission to publish memory.

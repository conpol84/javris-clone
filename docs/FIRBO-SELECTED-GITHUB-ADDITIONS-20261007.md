## Mem0 integration requirements

Mem0 is a memory engine, not an instruction card. The reviewed README defaults
to an OpenAI extraction LLM and text-embedding-3-small. Existing model catalogue
availability does not prove that FIRBO's authorized route supports embeddings,
structured extraction, cost bounds or the chosen vector dimensions.

Keep FIRBO Supabase project bfeinnsorgjycivozcau as the authoritative company
memory store. Existing company/employee memory and Knowledge semantic retrieval
must not be replaced or dropped. A later adapter must meet these checks:

- Explicit supported self-hosted service/version and authorized provider route.
  Disable cloud defaults, telemetry and autonomous ingestion until reviewed.
- Tenant and employee identity supplied server-side, never trusted from model
  arguments. Retrieval, writes and deletion stay within existing company scope.
- Preserve source task IDs, expiry, deletion and user corrections. Do not ingest
  credentials or every conversation automatically; define a minimal data policy.
- Meter extraction and embeddings separately through approved accounting;
  actual input/output pricing and model capabilities must be verified.
- Use synthetic fixture memories first: retrieval quality against the existing
  baseline, cross-company denial, deleted/expired exclusion, contradictory fact
  handling, outages and bounded latency. No real inference needed for transport
  tests. A real quality evaluation requires authorized provider acceptance.
- Default disabled with reversible fallback to existing FIRBO memory; no schema
  migration replay, second public database or unguarded network egress.

No installed Mem0 integration is claimed here. Missing runtime/provider and
quality evidence cannot be solved by renaming existing memory or adding a card.
